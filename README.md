# Inbound_demand_forecast_portfolio — 入庫実績から需給を予測するポートフォリオ

国内の3PL事業者(物流業務を請け負う会社)が、荷主からの入庫実績のパターンをもとに、今後の入荷・出荷量を予測する試作プロジェクトです。実データは一切使用せず、ダミーデータの生成から予測モデル・補充ロジックのシミュレーターまで一式を成果物としています。

## 背景と解決したい課題（Why）

3PL側からは、荷主がいつ・なぜ発注したかという発注理由そのものは見えません。ここで「発注の理由を推測する」という無理筋なアプローチを取るのではなく、**「これまでの入庫実績のパターンから今後を予測する」**という、3PLの立場から現実的に実行可能なアプローチを選んだことが設計の核心です。

さらに、荷主から週次の見込み数量(フォーキャスト)が提供されているにもかかわらず、それが実際の数量とどれだけ合っていたかの精度検証がこれまで行われていない、という現場の改善余地に直接応える設計にしています。

## 誰のためのツールか、どう自分たちに応用するか

**対象読者**: 3PLの入庫予測担当、特に「荷主の発注理由が見えない」という制約のもとで需給を読みたい人。

**応用方法**: `src/common/config.py`の`Settings`(`categories`・`skus_per_category`・`seasonal_index_by_month`・`replenishment_policy`等)を自社の商材構成に合わせて変更するだけで、同じ生成・予測・シミュレーターのパイプラインが動くように設計しています。実データを接続する場合は、`data/synthetic/inbound_demand_dummy.xlsx`と同じ3シート構成(商品マスタ・日々の入出庫実績・週次見込み数量)にExcelを整形すれば`run_forecast`にそのまま投入できます。

## 機能概要とアーキテクチャ（What / How）

3カテゴリ(ノートPC/デスクトップPC/モニター)×各10SKU=30SKU、2年分日次のダミーデータ(商品マスタ・日々の入出庫実績・週次見込み数量の3シート)をExcel形式で生成します。

- **需要予測モデル**: `Volume_forecast_portfolio`と同じ方法論(ベースライン=前週同曜日平均 vs LightGBM、2024年学習/2025年検証)を踏襲。全体WAPEは18.6%→15.6%まで改善。
- **週次見込みの精度検証**: モデルを使わず、荷主提供のフォーキャストと実績を直接比較(全体WAPE7.9%)。これまで未実施だった検証に初めて答えるものです。
- **荷主予測 vs 自前モデルの比較**: 全体では自社モデルがわずかに上回る(7.6%→7.1%)一方、カテゴリによっては荷主予測の方が精度が高いケースもあり、「常に自前モデルが優れているわけではなく、クロスチェックとして併用するのが妥当」という結論を正直に示しています。
- **補充ロジックのシミュレーター(Streamlit)**: 発注方式((s,S)型に統一)・リードタイム・安全在庫日数を画面上で調整し、欠品率・在庫推移への影響をその場で確認できます。

### 動かし方

```bash
pip install -r requirements.txt
python -m src.export_excel   # ダミーデータ生成
python -m src.run_forecast   # 予測モデル・精度検証
streamlit run app.py         # 補充ロジックシミュレーター
python -m pytest tests/ -v   # テスト(実データ・実API不使用)
```

## 現在のステータスと直面している課題（Current Status & Technical Challenges）

ダミーデータの生成、需要予測モデル・週次見込みの精度検証、補充ロジックのシミュレーターまでが完了し、テスト28件は全件パスしています。実装の過程で見つけて修正した技術的な壁を、経緯として明記しています。

**発見・解消した壁: 発注ロジックのlook-aheadリーク**

旧実装では、入庫ロットサイズを「期間全体(未来を含む)の平均需要」から決めていました。この結果、需要が指数関数的に減衰する終売間近のSKUでは、発注時点でまだ起きていない未来の低い需要まで均して見てしまい、期間前半のロットが恒常的に過小になる、という非現実的な偏り(終売間近SKUの欠品発生率が55〜70%に達する)が生じていました。発注日より前の実績だけを参照する方式(`compute_trailing_mean`)への書き換えで、現実的な水準(全体7.9%)に収束させています。この「未来を覗いてしまうバグ」は需要予測・在庫シミュレーション全般で起きやすい典型的な罠であり、気づいて直した経緯自体を成果物として明記する価値があると考えています。

**現在のスコープの限界**

人件費・コストへの換算、複数拠点を考慮したサプライチェーン全体の設計は、現時点では対象外です。単一拠点の需給予測に意図的にスコープを絞っています。

## 今後の展望（Next Steps）

- `Volume_forecast_portfolio`で実施済みの人時変換・ビジネス効果換算ロジックをこちらにも移植し、精度改善を金額換算する。
- 複数拠点間の在庫融通を考慮した拡張(ネットワーク全体最適化、`Network_design_optim`との接続可能性)。
- 荷主提供の週次見込みとのクロスチェックを自動化し、乖離が一定以上の場合にアラートを出す仕組み(現状は事後検証のみ)。生成AIを使って、乖離が大きい場合の要因を自然言語で要約する機能も視野に入れています。
